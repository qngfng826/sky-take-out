## 改造① 缓存三件套（穿透 / 击穿 / 雪崩防护）

### 1.1 为什么要改（原版问题盘点）

| 位置 | 课程原版实现 | 问题 |
|---|---|---|
| 用户端菜品查询 `user/DishController` | 裸 RedisTemplate get/set（key: `dish_16`） | ① 无穿透防护 ② 无击穿防护 ③ 空结果不缓存，反复查库 ④ value 用 JDK 序列化，redis-cli 里不可读 |
| 用户端套餐查询 `user/SetmealController` | Spring Cache `@Cacheable` | ① 默认 `RedisCacheConfiguration` **没有过期时间**，缓存永不失效 ② 注解模型拿不到互斥锁，无法防击穿 |
| 管理端清缓存 `admin/DishController` | `redisTemplate.keys("dish_*")` | `KEYS` 命令一次性遍历全部 key 并**阻塞 Redis 主线程**，生产环境是事故级操作 |
| key 管理 | `"dish_"` 字符串散落在 4 个类 5 处 | 改前缀必须全局搜替，漏改一处就产生"写了清不掉"的脏缓存 |

### 1.2 三个核心概念

**缓存穿透**：请求"数据库中根本不存在"的数据，缓存永远不会命中，每次都打到数据库。
经典攻击手法：`categoryId=-999`、`categoryId=99999999` 疯狂请求。
- 本实现方案：**空值缓存** —— 查库为空也缓存一个 `""`，给短 TTL（60 秒），之后相同 id 在 Redis 层直接拦截
- 备选方案：布隆过滤器（空间效率高，但有误判率、不能直接删除，黑马点评课程会讲）

**缓存击穿**：某个热点 key 在过期的一瞬间，大量并发同时未命中、同时查库重建，瞬时压垮数据库。
- 方案 A **互斥锁**（本实现，已接线）：`setIfAbsent` 抢锁，同一时刻只放行一个线程查库重建，其余线程休眠 50ms 后重试（重试时大概率命中重建好的缓存）
  - 强一致：拿不到新数据就不返回
  - 两个细节：锁必须带 TTL（防止持锁线程挂掉导致死锁）；拿到锁后要**双重检查**缓存（等锁期间可能已被重建）
- 方案 B **逻辑过期**（`CacheClient#queryWithLogicalExpire` 已实现，未接线）：key 不设 Redis TTL，value 里存 `expireTime`；过期后不阻塞、不删除，先返回旧数据，同时抢到锁的线程后台异步重建
  - 高可用：任何请求都不阻塞
  - 代价：重建完成前所有人都拿到旧数据（最终一致），且需要提前**预热**缓存
  - 两者取舍：强一致选互斥锁，高可用选逻辑过期

**缓存雪崩**：大量 key 在同一时刻集中失效（或 Redis 宕机），数据库瞬时被打爆。
- 缓解：TTL 加随机偏移量打散失效时间（本实现在 Controller 的 TTL 注释中留了说明位）；进一步是缓存集群 + 多级缓存

### 1.3 关键代码对照

**用户端菜品查询（before / after）：**

```java
// ===== 课程原版：裸 RedisTemplate，无任何防护 =====
String key = "dish_" + categoryId;
List<DishVO> list = (List<DishVO>) redisTemplate.opsForValue().get(key);
if (list != null && list.size() > 0) {
    return Result.success(list);
}
list = dishService.listWithFlavor(dish);
redisTemplate.opsForValue().set(key, list);          // 没有 TTL！
return Result.success(list);

// ===== 改造后：统一走 CacheClient（穿透+击穿防护，带 TTL） =====
List<DishVO> list = cacheClient.queryWithPassThroughList(
        RedisKeyConstant.CACHE_DISH_KEY, categoryId, DishVO.class,
        id -> {
            Dish dish = new Dish();
            dish.setCategoryId(id);
            dish.setStatus(StatusConstant.ENABLE);
            return dishService.listWithFlavor(dish);
        },
        CACHE_DISH_TTL, TimeUnit.MINUTES);
```

**互斥锁核心（CacheClient 内部）：**

```java
// setIfAbsent 即 Redis 的 SET NX PX，原子操作：只有第一个线程能写入成功
private boolean tryLock(String key) {
    Boolean ok = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    return Boolean.TRUE.equals(ok);
}
// 重建流程：抢锁 → 双重检查缓存 → 查库 → 写缓存 → finally 释放锁
```

**管理端清缓存（KEYS → SCAN）：**

```java
// 原版：KEYS 命令，阻塞 Redis 主线程
Set keys = redisTemplate.keys("dish_*");
redisTemplate.delete(keys);

// 改造后：SCAN 游标分批遍历，不阻塞（CacheClient#evictByPrefix）
try (Cursor<String> cursor = stringRedisTemplate.scan(
        ScanOptions.scanOptions().match(prefix + "*").count(1000).build())) {
    // 收集后批量删除
}
```

### 1.4 改造后的数据流

```
请求 categoryId=16
   │
   ├─ 缓存命中有效值 ──────────────▶ 直接返回（不查库）
   ├─ 缓存命中空值 "" ─────────────▶ 返回空（该分类确实无数据，已拦截穿透请求）
   │
   └─ 未命中 ──▶ 抢锁 lock:cache:dish:16
                  ├─ 抢到 ──▶ 双重检查 ──▶ 查库 ──▶ 有数据写缓存(30min) / 无数据写 ""(60s) ──▶ 返回
                  └─ 没抢到 ──▶ sleep 50ms ──▶ 回到"查缓存"（大概率命中）
```

### 1.5 效果（JMeter 压测已回填，2026-11-15）

**压测方法**：JMeter 5.6.3 CLI 模式，50 并发。基线 = 改造前课程代码（git worktree 检出 9a2c67e）打进**与生产完全相同的容器环境**（同基础镜像 eclipse-temurin:8-jre、同 compose 网络、同外置配置），唯一变量是代码版本；DB 查询次数用 **MySQL general log** 逐条取证（应用侧日志不可靠时它是数据库侧铁证）。脚本与 HTML 报告见 `doc/jmeter/`。

**场景① 缓存命中（categoryId=16，预热后 50 并发 × 30s）**

| 指标 | 基线（课程基础缓存） | 改造后（CacheClient） |
|---|---|---|
| TPS | 12,913 | 13,066 |
| P95 / P99 | 7ms / 9ms | 7ms / 8ms |
| 期间 DB 查询次数 | 0 | 0 |

> 命中路径两者都走 Redis，性能相当——**收益不在这里，在下面两个故障场景**。

**场景② 缓存击穿（删除热点 key 后 50 线程瞬时齐发，ramp-up=0）**

| 指标 | 基线（无互斥锁） | 改造后（互斥锁） |
|---|---|---|
| 30s 内 DB 查询次数 | **200 条**（50 线程 × 4 条 SQL 全部穿透查库） | **4 条**（仅 1 个连接完成 1 轮重建） |
| TPS / P95 / P99 | 13,419 / 7ms / 9ms | 12,930 / 8ms / 10ms |

> general log 铁证：基线的 200 条查询来自 4 个不同连接、集中在 **4ms 内**同时到达（重建风暴）；改造后仅 1 个连接顺序完成 1 轮重建，其余 49 个线程等锁后直接命中缓存。**击穿场景 DB 瞬时压力降低 98%（200 → 4）**。

**场景③ 缓存穿透（不存在的分类 id=-999，50 并发 × 60s）**

| 指标 | 基线（空结果不缓存，每请求查库） | 改造后（空结果被缓存拦截） |
|---|---|---|
| TPS | 7,230 | **14,511（+100%）** |
| P95 / P99 | 12ms / 17ms | **6ms / 8ms** |
| 60s 内 DB 查询次数 | **433,377 条（= 请求数，每请求 1 条）** | **1 条**（仅首次查询） |

**结论**：改造的收益不在缓存命中路径（命中时大家都走 Redis），而在**故障场景**——击穿时 DB 瞬时压力降 98%，穿透时无效流量对 DB 的影响从"每请求 1 次查库"降为 0，同时该场景 TPS 翻倍、P99 降半。这就是"缓存三件套"的意义：**故障发生时保护数据库**。

## 改造② 订单超时取消：定时任务轮询 → RabbitMQ 延迟消息

### 2.1 为什么要改

课程原版 `OrderTask#processTimeoutOrders`：**每分钟轮询一次全表**（`status=待支付 AND order_time < 15分钟前`）：

| 问题 | 说明 |
|---|---|
| 超时判定误差大 | 订单实际可能 15~16 分钟才被取消，卡着 15 分钟的场景永远有 1 分钟误差 |
| 恒定的数据库压力 | 订单量 10 万时，每分钟扫一遍表，绝大多数轮询都是空转 |
| 无法精确到"单订单" | 轮询是批量语义，无法对单个订单做到点即处理 |

**延迟消息方案**：下单成功的那一刻，投递一条"15 分钟后才到达"的消息；到点后消费者拿到 orderId，精准检查这一个订单。没有超时风险时，系统零开销。

### 2.2 延迟插件 vs 死信队列（面试高频考点）

| 维度 | TTL + 死信队列（DLX） | 延迟插件（本实现） |
|---|---|---|
| 是否需要装插件 | 否，RabbitMQ 原生 | 是（`rabbitmq_delayed_message_exchange`） |
| 原理 | 消息带 TTL 进队列，过期无人消费则转入死信交换机 | 交换机类型 `x-delayed-message`，消息带 `x-delay` 头在交换机内暂存，到期才路由 |
| 队头阻塞 | **有**：队头一条 15 分钟的消息会阻塞它后面 1 分钟到期的消息 | **无** |
| 支持多种延迟时长 | 每种 TTL 需要单独建一个队列，笨重 | 每条消息自带 delay，任意时长混发 |

本项目本地用 Docker 运行 RabbitMQ，启用插件只需两条命令（见 README 快速开始），故选延迟插件。

### 2.3 消息流转与关键代码

```
submitOrder（下单成功）
   │ convertAndSend + x-delay=900000ms
   ▼
sky.order.delay.exchange（x-delayed-message，暂存消息）
   │ 到期后按 direct 语义路由
   ▼
sky.order.delay.queue
   │ @RabbitListener
   ▼
OrderDelayListener.processTimeoutOrder(orderId)
   │ 查库校验：仅"待支付"才取消（幂等防护）
   ▼
订单置为 CANCELLED + 取消原因
```

**发送端（`OrderServiceImpl.submitOrder` 末尾）：**

```java
rabbitTemplate.convertAndSend(RabbitMQConfiguration.ORDER_DELAY_EXCHANGE,
        RabbitMQConfiguration.ORDER_DELAY_ROUTING_KEY,
        orders.getId(),
        message -> {
            message.getMessageProperties().setDelay(orderDelaySeconds * 1000);
            return message;
        });
```

**消费端（`OrderDelayListener`）：**

```java
@RabbitListener(queues = RabbitMQConfiguration.ORDER_DELAY_QUEUE)
public void processTimeoutOrder(Long orderId) {
    Orders ordersDB = orderMapper.getById(orderId);
    // 幂等防护：15 分钟里订单可能已被支付/取消，只有仍"待支付"才取消
    if (ordersDB == null || !Orders.PENDING_PAYMENT.equals(ordersDB.getStatus())) {
        return;
    }
    // 置 CANCELLED + 取消原因
}
```

### 2.4 两个必须处理的正确性问题（可以在面试中主动讲）

1. **幂等 / 状态校验**：消息在路上的 15 分钟里订单状态可能已变化，监听器必须先查库确认仍是"待支付"才取消——否则会把用户刚付完钱的订单取消掉。
2. **事务与消息的一致性**：发送消息发生在 `@Transactional` 提交之前，若事务随后回滚，监听器会收到"幽灵消息"。当前用监听器查库兜底（订单不存在则跳过）；严格方案是本地消息表或 RocketMQ 事务消息（黑马 MQ 课程会讲）。

### 2.5 效果（待压测回填）

| 指标 | 改造前（轮询） | 改造后（延迟消息） |
|---|---|---|
| 超时取消的及时性 | 最大误差 1 分钟 | 精准到秒（消息到点即处理） |
| 空闲时段数据库压力 | 每分钟一次全表扫描 | 0（无消息无开销） |

## 改造③ 报表统计 SQL 索引优化（EXPLAIN 驱动）

### 3.1 现状与问题

orders / order_detail / user 三表在原版 sky.sql 中**只有主键索引**，而报表与工作台的全部统计 SQL 都跑在这三张表上：

| SQL（Mapper） | 用途 | WHERE 特征 |
|---|---|---|
| OrderMapper.xml `sumByMap` / `countByMap` | 营业额 / 订单统计 | `order_time` 范围（逐日循环）+ 可选 `status` 等值 |
| OrderMapper.java `countStatus` | 管理端订单数量统计 | 仅 `status` 等值 |
| OrderDetailMapper.xml `getSalesTop10` | 销量 Top10 | join orders（`status=5` + 日期范围），按 `od.order_id` 关联 |
| UserMapper.xml `countByMap` | 用户统计 | `create_time` 范围（逐日循环） |

关键发现：`status` **可能为 null** 的调用真实存在——订单统计的"订单总数"、工作台总订单数/全部订单都是纯 `order_time` 范围查询。因此单一 `(status, order_time)` 索引覆盖不了全部模式，orders 需要两个索引。

### 3.2 索引设计

```sql
ALTER TABLE orders       ADD INDEX idx_status_order_time (status, order_time),   -- 等值在前、范围在后
                         ADD INDEX idx_order_time (order_time);
ALTER TABLE order_detail ADD INDEX idx_order_id_cover (order_id, name, number);  -- 覆盖索引
ALTER TABLE user         ADD INDEX idx_create_time (create_time);
```

- `(status, order_time)`：等值列在前、范围列在后，服务"按状态 + 日期"的报表查询
- `(order_time)`：服务无 status 条件的日期范围查询——**两类访问模式各一个索引**
- order_detail 用 `(order_id, name, number)` **覆盖索引**而不是单列 `(order_id)`：第一次实验中单列索引让 Q4 反而变慢（207ms→363ms——优化器改为以 orders 驱动后，5.8 万次随机**回表**比顺序全扫更贵）；换成覆盖索引消除回表后降至 158ms。这是"索引不是加了就快，要用 EXPLAIN 验证"的直接证据
- 索引已固化进 `doc/sky.sql`（新环境初始化即有）；10w 级基准数据脚本见 `doc/benchmark-data.sql`（数据仅在本机容器数据卷，`down -v` 后重跑脚本即可恢复）

### 3.3 EXPLAIN 前后对比（orders 10w / order_detail 20w / user 500，EXPLAIN ANALYZE 实测）

| 查询 | 前：type / rows | 后：type / key / rows | 耗时 |
|---|---|---|---|
| Q1 营业额（单日，status=5） | ALL / 99,000 | range / idx_status_order_time / 1,957 | 20.6ms → **2.85ms（7.2×）** |
| Q2 订单总数（单日，无 status） | ALL / 99,000 | range / idx_order_time / 3,426（覆盖索引） | 18.9ms → **0.75ms（25×）** |
| Q3 工作台全部订单（今日 0 点起） | ALL / 99,000 | range / idx_order_time / 2,340（覆盖索引） | 18.6ms → **0.47ms（40×）** |
| Q4 销量 Top10（30 天 join） | od 全表扫 20w + 临时表/filesort | o 覆盖 range + od 覆盖 ref | 207ms → **158ms（-24%）**，扫描行数 40w → 17.6w |
| Q5 用户统计（单日） | ALL / 500 | range / idx_create_time（覆盖索引） | 0.096ms → 0.021ms（小表，收益在规模化后） |
| Q6 countStatus（status=2） | ALL / 99,000 | ref / idx_status_order_time / 14,370（覆盖索引） | 18.3ms → **1.0ms（18×）** |

### 3.4 结论

- 报表是**逐日循环查询**（30 天报表 = 30+ 次查询），每次扫描从 9.9 万行全表扫描降为千行级索引范围扫描；Q2/Q3/Q5/Q6 四条做到覆盖索引（免回表）；
- Q4 的最大收获不是百分比而是**方法论**：单列索引让查询变慢 75%，覆盖索引才真正解决问题——所有索引决策以 `EXPLAIN` / `EXPLAIN ANALYZE` 实测为准，不凭感觉加索引；
- 延伸建议（不在本次范围）：`user.openid` 是微信登录热路径（`getByOpenid`），同样无索引，规模化前建议补唯一索引。

## 改造④ 支付幂等（状态机 + 条件更新 + 分布式锁）

### 4.1 现状与真实后果（不只是一个面试话术）

| 缺陷位置 | 原状 | 真实后果 |
|---|---|---|
| `OrderServiceImpl.payment` | 无任何校验/锁（微信调用被注释走 mock，直接调 paySuccess） | 已取消订单照样"支付成功"；同一订单可无限次重复支付 |
| `OrderServiceImpl.paySuccess` | `getByNumber` 后**无条件 update** status=2/已支付 + 推来单提醒 | ① 超时取消（status=6）的订单被迟到的回调"复活"成待接单；② 重复回调把已接单/已完成订单反复改写 checkout_time；③ WebSocket 来单提醒重复弹窗 + 提示音 |
| `PayNotifyController` | 回调直接调 paySuccess，无幂等 | 微信回调官方就会重试，②③ 被放大 |

### 4.2 三层防护设计

```text
请求 → ①前置校验（存在/归属/状态） → ②Redis 互斥锁 lock:pay:{orderId} 30s → ③数据库条件更新（WHERE status=1） → WebSocket 推送
```

- **第一层（前置校验）**：订单存在 + 归属当前用户（`BaseContext`）+ `status=PENDING_PAYMENT`，否则抛明确业务异常（"订单已取消，无法支付"等）——把绝大多数非法请求挡在最外层，文案可直达用户；
- **第二层（Redis 锁）**：`cacheClient.tryLock("lock:pay:" + orderId, 30s)`——前置校验存在 TOCTOU 并发窗口（两个请求同时读到 status=1），锁保证同一订单同一时刻只有一个支付流程在执行；复用改造① CacheClient 的 setIfAbsent（SET NX PX 原子操作），TTL 兜底防死锁，finally 释放；
- **第三层（条件更新兜底）**：`UPDATE orders SET status=2 ... WHERE id=? AND status=1`——数据库行级原子性，**无论前两层发生什么，状态流转有且仅有一次**；affected=0 即幂等命中，paySuccess 返回 false 不推 WebSocket，payment 向上抛"订单状态已变更"；
- **回调幂等**：重复回调命中第三层返回 false，仍正常应答微信 success（避免重试风暴）。

**关键取舍（面试可讲）**：状态流转为什么用**条件更新**而不是"查了再改"？查-改-写在并发下有 TOCTOU 竞态（两个事务都读到 1、都写 2、都推提醒）；条件更新把校验和写入合并为一次原子操作，affected 行数天然就是"是否首次"的判定。Redis 锁防的是**流程级**重复进入，条件更新才是**最终一致性**保证——两层不是冗余，是不同层面的防护。

与既有亮点的呼应：改造①互斥锁（缓存重建防击穿）→ 改造②监听器状态校验（订单取消幂等）→ 改造④（支付幂等），同一套"状态机 + 原子操作"思想贯穿缓存、消息、资金三个场景。
