## 改造① 缓存三件套（穿透 / 击穿 / 雪崩防护）

### 1.1 为什么要改（原版问题盘点）

| 位置 | 课程原版实现 | 问题 |
|---|---|---|
| 用户端菜品查询 `user/DishController` | 裸 RedisTemplate get/set（key: `dish_16`） | ① 无穿透防护 ② 无击穿防护 ③ 空结果不缓存，反复查库 ④ value 用 JDK 序列化，redis-cli 里不可读 |
| 用户端套餐查询 `user/SetmealController` | Spring Cache `@Cacheable` | ① 默认 `RedisCacheConfiguration` **没有过期时间**，缓存永不失效 ② 注解模型拿不到互斥锁，无法防击穿 |
| 管理端清缓存 `admin/DishController` | `redisTemplate.keys("dish_*")` | `KEYS` 命令一次性遍历全部 key 并**阻塞 Redis 主线程**，生产环境是事故级操作 |
| key 管理 | `"dish_"` 字符串散落在 4 个类 5 处 | 改前缀必须全局搜替，漏改一处就产生"写了清不掉"的脏缓存 |

### 1.2 三个核心概念

**缓存穿透**：请求"数据库中根本不存在"的数据，缓存永远不会命中，每次都打到数据库。
经典攻击手法：`categoryId=-999`、`categoryId=99999999` 疯狂请求。
- 本实现方案：**空值缓存** —— 查库为空也缓存一个 `""`，给短 TTL（60 秒），之后相同 id 在 Redis 层直接拦截
- 备选方案：布隆过滤器（空间效率高，但有误判率、不能直接删除，黑马点评课程会讲）

**缓存击穿**：某个热点 key 在过期的一瞬间，大量并发同时未命中、同时查库重建，瞬时压垮数据库。
- 方案 A **互斥锁**（本实现，已接线）：`setIfAbsent` 抢锁，同一时刻只放行一个线程查库重建，其余线程休眠 50ms 后重试（重试时大概率命中重建好的缓存）
  - 强一致：拿不到新数据就不返回
  - 两个细节：锁必须带 TTL（防止持锁线程挂掉导致死锁）；拿到锁后要**双重检查**缓存（等锁期间可能已被重建）
- 方案 B **逻辑过期**（`CacheClient#queryWithLogicalExpire` 已实现，未接线）：key 不设 Redis TTL，value 里存 `expireTime`；过期后不阻塞、不删除，先返回旧数据，同时抢到锁的线程后台异步重建
  - 高可用：任何请求都不阻塞
  - 代价：重建完成前所有人都拿到旧数据（最终一致），且需要提前**预热**缓存
  - 两者取舍：强一致选互斥锁，高可用选逻辑过期

**缓存雪崩**：大量 key 在同一时刻集中失效（或 Redis 宕机），数据库瞬时被打爆。
- 缓解：TTL 加随机偏移量打散失效时间（本实现在 Controller 的 TTL 注释中留了说明位）；进一步是缓存集群 + 多级缓存

### 1.3 关键代码对照

**用户端菜品查询（before / after）：**

```java
// ===== 课程原版：裸 RedisTemplate，无任何防护 =====
String key = "dish_" + categoryId;
List<DishVO> list = (List<DishVO>) redisTemplate.opsForValue().get(key);
if (list != null && list.size() > 0) {
    return Result.success(list);
}
list = dishService.listWithFlavor(dish);
redisTemplate.opsForValue().set(key, list);          // 没有 TTL！
return Result.success(list);

// ===== 改造后：统一走 CacheClient（穿透+击穿防护，带 TTL） =====
List<DishVO> list = cacheClient.queryWithPassThroughList(
        RedisKeyConstant.CACHE_DISH_KEY, categoryId, DishVO.class,
        id -> {
            Dish dish = new Dish();
            dish.setCategoryId(id);
            dish.setStatus(StatusConstant.ENABLE);
            return dishService.listWithFlavor(dish);
        },
        CACHE_DISH_TTL, TimeUnit.MINUTES);
```

**互斥锁核心（CacheClient 内部）：**

```java
// setIfAbsent 即 Redis 的 SET NX PX，原子操作：只有第一个线程能写入成功
private boolean tryLock(String key) {
    Boolean ok = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, "1", LOCK_TTL_SECONDS, TimeUnit.SECONDS);
    return Boolean.TRUE.equals(ok);
}
// 重建流程：抢锁 → 双重检查缓存 → 查库 → 写缓存 → finally 释放锁
```

**管理端清缓存（KEYS → SCAN）：**

```java
// 原版：KEYS 命令，阻塞 Redis 主线程
Set keys = redisTemplate.keys("dish_*");
redisTemplate.delete(keys);

// 改造后：SCAN 游标分批遍历，不阻塞（CacheClient#evictByPrefix）
try (Cursor<String> cursor = stringRedisTemplate.scan(
        ScanOptions.scanOptions().match(prefix + "*").count(1000).build())) {
    // 收集后批量删除
}
```

### 1.4 改造后的数据流

```
请求 categoryId=16
   │
   ├─ 缓存命中有效值 ──────────────▶ 直接返回（不查库）
   ├─ 缓存命中空值 "" ─────────────▶ 返回空（该分类确实无数据，已拦截穿透请求）
   │
   └─ 未命中 ──▶ 抢锁 lock:cache:dish:16
                  ├─ 抢到 ──▶ 双重检查 ──▶ 查库 ──▶ 有数据写缓存(30min) / 无数据写 ""(60s) ──▶ 返回
                  └─ 没抢到 ──▶ sleep 50ms ──▶ 回到"查缓存"（大概率命中）
```

## 改造② 订单超时取消：定时任务轮询 → RabbitMQ 延迟消息

### 2.1 为什么要改

课程原版 `OrderTask#processTimeoutOrders`：**每分钟轮询一次全表**（`status=待支付 AND order_time < 15分钟前`）：

| 问题 | 说明 |
|---|---|
| 超时判定误差大 | 订单实际可能 15~16 分钟才被取消，卡着 15 分钟的场景永远有 1 分钟误差 |
| 恒定的数据库压力 | 订单量 10 万时，每分钟扫一遍表，绝大多数轮询都是空转 |
| 无法精确到"单订单" | 轮询是批量语义，无法对单个订单做到点即处理 |

**延迟消息方案**：下单成功的那一刻，投递一条"15 分钟后才到达"的消息；到点后消费者拿到 orderId，精准检查这一个订单。没有超时风险时，系统零开销。

### 2.2 延迟插件 vs 死信队列（面试高频考点）

| 维度 | TTL + 死信队列（DLX） | 延迟插件（本实现） |
|---|---|---|
| 是否需要装插件 | 否，RabbitMQ 原生 | 是（`rabbitmq_delayed_message_exchange`） |
| 原理 | 消息带 TTL 进队列，过期无人消费则转入死信交换机 | 交换机类型 `x-delayed-message`，消息带 `x-delay` 头在交换机内暂存，到期才路由 |
| 队头阻塞 | **有**：队头一条 15 分钟的消息会阻塞它后面 1 分钟到期的消息 | **无** |
| 支持多种延迟时长 | 每种 TTL 需要单独建一个队列，笨重 | 每条消息自带 delay，任意时长混发 |

本项目本地用 Docker 运行 RabbitMQ，启用插件只需两条命令（见 README 快速开始），故选延迟插件。

### 2.3 消息流转与关键代码

```
submitOrder（下单成功）
   │ convertAndSend + x-delay=900000ms
   ▼
sky.order.delay.exchange（x-delayed-message，暂存消息）
   │ 到期后按 direct 语义路由
   ▼
sky.order.delay.queue
   │ @RabbitListener
   ▼
OrderDelayListener.processTimeoutOrder(orderId)
   │ 查库校验：仅"待支付"才取消（幂等防护）
   ▼
订单置为 CANCELLED + 取消原因
```

**发送端（`OrderServiceImpl.submitOrder` 末尾）：**

```java
rabbitTemplate.convertAndSend(RabbitMQConfiguration.ORDER_DELAY_EXCHANGE,
        RabbitMQConfiguration.ORDER_DELAY_ROUTING_KEY,
        orders.getId(),
        message -> {
            message.getMessageProperties().setDelay(orderDelaySeconds * 1000);
            return message;
        });
```

**消费端（`OrderDelayListener`）：**

```java
@RabbitListener(queues = RabbitMQConfiguration.ORDER_DELAY_QUEUE)
public void processTimeoutOrder(Long orderId) {
    Orders ordersDB = orderMapper.getById(orderId);
    // 幂等防护：15 分钟里订单可能已被支付/取消，只有仍"待支付"才取消
    if (ordersDB == null || !Orders.PENDING_PAYMENT.equals(ordersDB.getStatus())) {
        return;
    }
    // 置 CANCELLED + 取消原因
}
```

### 2.4 两个必须处理的正确性问题（可以在面试中主动讲）

1. **幂等 / 状态校验**：消息在路上的 15 分钟里订单状态可能已变化，监听器必须先查库确认仍是"待支付"才取消——否则会把用户刚付完钱的订单取消掉。
2. **事务与消息的一致性**：发送消息发生在 `@Transactional` 提交之前，若事务随后回滚，监听器会收到"幽灵消息"。当前用监听器查库兜底（订单不存在则跳过）；严格方案是本地消息表或 RocketMQ 事务消息（黑马 MQ 课程会讲）。

### 2.5 效果（待压测回填）

| 指标 | 改造前（轮询） | 改造后（延迟消息） |
|---|---|---|
| 超时取消的及时性 | 最大误差 1 分钟 | 精准到秒（消息到点即处理） |
| 空闲时段数据库压力 | 每分钟一次全表扫描 | 0（无消息无开销） |

## 本地验证步骤

```bash
# 1. 启动 RabbitMQ（含延迟插件，两条命令 + 重启）
docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3.13-management
docker exec rabbitmq rabbitmq-plugins enable rabbitmq_delayed_message_exchange
docker restart rabbitmq
# 管理界面：http://localhost:15672 （guest/guest）

# 2. 启动后端（RabbitMQ 连接成功后才会声明交换机/队列）
```

**缓存验证**：
- 访问一次用户端菜品列表 → `redis-cli` 中出现 `cache:dish:16`，TTL 约 30 分钟
- 请求一个不存在的分类 id → 出现值为 `""` 的 key，TTL 约 60 秒（穿透防护生效）
- 管理端修改/删除该分类菜品 → 对应 key 被清掉（SCAN 清理生效）

**MQ 验证**：
- 把 `application-dev.yml` 的 `sky.order.delay-seconds` 临时改为 `10`，重启
- 下单不支付 → 10 秒后日志出现"订单超时未支付，已自动取消"
- 下单后立即支付 → 10 秒后日志出现"订单不存在或状态已变更，跳过超时取消"（幂等防护生效）
- RabbitMQ 管理界面能看到 `sky.order.delay.exchange`（type: x-delayed-message）和 `sky.order.delay.queue`
